## 2b. Learned complaint classifier (hybrid with the lexicon)

`make train`: TF-IDF (character 2–5-grams + word 1–2-grams) and logistic regression, trained on TRAIN complaints whose administrator reply names a rule code or an appeal verdict (29516 weak «silver» labels). Final category = 0.6 × model probability + (1 − 0.6) × normalised lexicon score; the model's weight shrinks when most words of the text were never seen in training; `complaint.invalid`, reports, safety flags, priority raises and human handoff stay rule-based. The weight was chosen on a reporter-grouped hold-out of TRAIN (best there: 0.7); VALID was used only to confirm. **Silver agreement is not hidden-test accuracy.**

| set | silver-labelled complaints | lexicon agreement | lexicon macro-F1 | model agreement | model macro-F1 | hybrid agreement | hybrid macro-F1 |
|---|---|---|---|---|---|---|---|
| TRAIN hold-out (by reporter) | 6112 | 0.8581 | 0.5949 | 0.9097 | 0.7389 | 0.9154 | 0.6606 |
| VALID (confirmation) | 350 | 0.8457 | 0.6639 | 0.9 | 0.8323 | 0.9 | 0.7436 |

The hybrid's macro-F1 is below the model's alone because the hybrid also predicts `complaint.invalid`, a class that silver labels never contain (macro-F1 is averaged over the union of classes). Main correction over the lexicon: appeals written by the punished player (artificial example: «я не использовал софт, проверьте ещё раз») that the lexicon labelled by the violation word are now `complaint.admin`. ### 3b. Independent AI-assisted review (NOT human, small, biased)

110 unambiguous tickets of the train-derived dev sample were labelled by an AI assistant, blind to the service output (ambiguous rows excluded). The classifier was tuned on this sample after a first pass (category accuracy 0.50 → see below), so the number is optimistic. Category accuracy **0.8455**, priority macro-F1 **0.8928**, priority accuracy 0.9182. Per detected language: kk n=14 acc=0.786, ru n=65 acc=0.831, uz n=30 acc=0.9, und n=1 acc=1.0. This is a bug-finding tool; **it is not Accuracy/macro-F1 and does not replace human labels** (see `docs/WHY_NO_ACCURACY.md`).

### 3b2. Rule retrieval (RAG), weak ground truth

On 5169 real complaints whose admin reply names a numbered rule: plain BM25 finds that rule at rank 1/3/5 in 2.9% / 5.8% / 17.5% of cases; BM25 with the jargon expansion (оск→оскорбление…) in 65.7% / 74.1% / 74.9%. The service does not trust retrieval alone: it cites a curated, anchor-checked candidate, and when it cites, the rule equals the admin's rule in 91.2% of cases (coverage 94.7%). Semantic (embedding) retrieval was not added: with tickets of 12–30 characters in slang, the measured bottleneck is vocabulary, which the expansion fixes; no measurement shows an embedding model would help, and it would add a dependency.

### 3c. Duplicate detection (weak check against the admins' verdict «duplicate»)

On 119337 real tickets in chronological order (author = `reporter_hash`, target = `reported_hash`, 60-minute window) 5567 were flagged. Only 1478 tickets carry the admin verdict `duplicate`; we cover recall 0.3024 of them at precision 0.0803 (admins close repeated complaints with other verdicts too, every repeated «помогите» of one author is flagged by us but has no verdict, and the policy now requires shared event details or a clear paraphrase instead of the bare category, so the number is lower and more conservative than before). This is a weak check, not the hidden-test labelling, which is unknown. Flagged by admin verdict: {'null': 3012, 'other': 761, 'duplicate': 447, 'approved': 368, 'invalid_format': 255, 'rejected': 243, 'need_evidence': 197, 'already_punished': 132, 'appeal_rejected': 112, 'appeal_approved': 23, 'closed': 17}.

**Related complaints** (other authors about the same accused player within 24 h, shown to the admin, never merged): 7516 of 68502 complaints have them. Weak check: the admin verdict «already punished» occurs in 1.40% of complaints with related ones vs 1.24% without, i.e. **no measurable predictive value** in this data (TRAIN holds only 20 % of reporters, so most related complaints are missing). It is offered as context for the admin, not as a decision signal.

## 5. Latency

* p50 **19.98 ms**, p95 **34.46 ms**, p99 50.55 ms, max 107.59 ms
* n = 1000 sequential HTTP requests to `POST /triage` (httpx keep-alive on 127.0.0.1)
* mode: template (demo: no LLM key, no model calls); machine: {'os': 'Windows-11-10.0.26200-SP0', 'python': '3.14.0', 'cpus': 12}
* template mode: no network model call is included. LLM mode adds one model call per ticket (see docs/REPORT.md).
* LLM mode: see the three tiers of evidence below (section 6b). The service enforces a hard wall-clock budget per ticket (`LLM_TOTAL_BUDGET_S`, default 4 s): the caller stops waiting at the deadline, a task that waited past it in the queue sends nothing (tested with a slow-drip server and 10 concurrent calls).

## 6. Cost per ticket

* Template mode (default, the mode all numbers above come from): **no external calls, $0.00 per ticket**, no GPU.
* LLM mode (optional): one model call per ticket (one extra call only if the provider rejects an optional field; the rejected request's cost is then reported as UNKNOWN, not as free). Official price for Claude Haiku 5.5 (checked 2026-10-30): $0.10 / MTok input, $0.50 / MTok output for prompts up to 100k tokens (<https://platform.claude.com/docs/en/about-claude/pricing>); the model page says it uses the newer tokenizer (~30 % more tokens than Haiku 4.5) and that adaptive thinking is on by default, so the request disables thinking and sets low effort, and does not send `temperature` (the page says to omit it).
* Measured prompt size on the 14 artificial demo tickets: mean 2941 characters, max 3134 characters (system prompt + facts + rule topics + the ticket + a reference template). With a pessimistic 2 characters per token that is ≈ 1470 / 1567 input tokens. **Projection (not a measurement):** mean ≈ $0.00027 per ticket (250 output tokens), worst case ≈ $0.00038 (450 output tokens, longest prompt) — that would be below the $0.002 target only IF the prices copied by hand from the provider's page and the 2-characters-per-token estimate are right. **Compliance with the cost limit is NOT claimed** until a real call is measured (`make llm-smoke`); with prices configured the service also enforces a per-ticket ceiling (it lowers `max_tokens` or skips the call), and without prices it reports the cost as unknown. The real value is recorded per call in the batch statistics (`pred.jsonl.stats.json`).

### 6b. LLM mode: three tiers of evidence, kept apart

1. **Mock tests (this repository, every run):** request shape of both providers, malformed answers, timeouts, the hard deadline, the queue, unknown cost, and the guard against unsafe model text (`tests/test_review3-5.py`, `tests/test_gemini.py`).
2. **Real calls on artificial tickets:** one run by the project author on 2026-10-31 with gemini `gemini-3.5-flash-lite` (18 artificial demo tickets x 2 (tests/fixtures/demo_tickets.jsonl), no real player data): 28 calls, 17 drafts accepted (rate 0.607), triage p50/p95 1027/1368 ms, measured cost per ticket: None (prices were not configured, so the cost is UNKNOWN). **This run was not repeated by the independent review, and it was made BEFORE the closed-vocabulary guard of the fifth review, which rejects more model sentences: the acceptance rate of the current code against a real model is unknown.**
3. **Real player tickets:** never sent to any external model (the evaluation scripts force `LLM_ENABLED=0`; a free tier may use submitted text for training).

Consequently compliance with the $0.002 per-ticket limit in LLM mode is **not demonstrated**: it is a projection (below) plus an enforced worst-case ceiling when prices are configured.

## 7. Safety checks (automated, see `tests/`)

Existence + relevance + applicability of every citation (section-aware, anchor words in the real rule text, place-bound rules need the place), wrong/non-existent rule numbers typed by the player, no promises of punishment/unban/refund in ru/en/kk/uz/es/pt, no claim that attachments were viewed or that the ticket was passed on, mandatory handoff and p0 for payments, hacks, lost access, threats and appeals also inside mixed tickets, prompt injection, broken/malicious/promising model output falling back to the template (the reason is written to `reasons`), dedup (author + accused + event details + time window, history survives a restart, different authors never merged), CLI == API, administrator text never reaches the pipeline. **These checks narrow the risk; they do not prove that no unsafe sentence can appear in LLM mode.** Zero findings of the internal audit mean that none of ITS checks fired, not that the drafts contain no semantic error; «technically valid citation» means the point exists, passes its anchor words and is named, not that it is the right rule for the event.

## 9. Limitations (short; full list in `docs/LIMITATIONS.md`)

* No human-labelled evaluation yet; hidden-test accuracy is unknown.
* Kazakh/Uzbek drafts are template-based and not reviewed by native speakers; only 31 kk and 119 uz tickets exist in the validation file.
* The category/priority rules follow a **draft** taxonomy; priority for help requests (p2), scams (p1/p2) and «complaints with proof» (category decides, evidence does not) is our interpretation.
* LLM mode: one real run on artificial tickets exists (author's, Gemini free tier, before the current guard); the current code's acceptance rate, real cost and latency are **not measured**.
* The sensitive-topic lexicon is tested on authors' phrasings; the real files contain very few such tickets, so its recall on unseen phrasing is unknown.
* Duplicate detection has no labelled data; kk/uz drafts are not reviewed by native speakers.
